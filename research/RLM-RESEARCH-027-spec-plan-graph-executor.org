* Research Question

Can the runtime support a model-authored *project plan language* — a typed,
closed-vocabulary plan dependency graph (`step/2`, `depends_on/2`,
`ready_step/1`) over project ops (`sync_remote/1`, `index/1`, `search/2`,
`locate/1`, `read/1`, `diff/2`, `edit/2`, `create/2`, `delete/1`, `run/1`,
`validate/1`, `delegate/2`) plus a normalized `symbol_ref` -> `source_span`
contract — without creating a second plan interpreter, a second scheduler, or
any path from model data to unrestricted execution?

The originating request also asks for a SPEC language with clauses
`goal/1, input/1, require/1, constraint/1, artifact/1, validate/1,
success/1`.  This record checks how much of that already exists in canonical
`main` and isolates the true gap.

* Findings (execution truth)

** F1: A closed-AST plan runtime already exists.

=rlm_plan= parses model JSON (or a =plan(Steps)= term) into a closed AST:

#+begin_example
context/3, model/4, rlm/2, tool/3, spawn_agent/3,
parallel/2, retry/3, checkpoint/1, final/1
#+end_example

plus closed expressions =literal/1, input/1, var/1, field/2, list/1,
object/1= (=prolog/rlm_plan.pl= lines 112-142, 280+).  Unknown ops are
rejected during normalization (=normalize_dict_step(Op, _, _) :- throw(...)=,
line 201) and at validation (=validate_step= fallback,
=prolog/rlm_plan.pl:479-481=; the ~1009 fallback is the execute-phase
belt-and-braces).  Tests pin that =call(shell(...))= style output never
reaches execution (=test/rlm_plan_test.pl=
"raw_call_term_is_rejected_during_validation").  The file is 1632 lines.

** F2: Whole-plan validation precedes any side effect.

=plan_validate/4= checks vocabulary, single trailing =final/1=, variable
binding, capability subset, recursive budget estimate
(=docs/typed-plans.md= "Whole-plan validation").  Execution preflight
verifies providers/tools exist before the first step
(=preflight_runtime/2=, =prolog/rlm_plan.pl= ~line 800).

** F3: Capabilities and expert closures are host-owned.

Per-op capability requirements (=context_capability/2=, =require_capability/2=
lines 577-587); tools/providers only resolve through host registries
=tools([tool(Name, Handler)])= / =providers([provider_ref(Name, Term)])=
(lines 760-790).  Model data cannot construct the callable.  This is the
"expert KB decides who executes" substrate.

** F4: SPEC language already covers the requested clause set (richer).

=rlm_spec_lang= structural catalog: =spec/1, schema_version/1, subject/1,
require/2-3, optional/2-3, invariant/1, output_contract/1, provenance/1,
assertion/2-3, evidence_policy/1=, desugared via =foldl(apply_form)= and
then =spec_normalize -> spec_validate -> spec_freeze=.  Requirement and
invariant forms may repeat; singleton forms (=schema_version/1=,
=subject/1=, =output_contract/1=, =provenance/1=) reject duplicates
(=set_singleton=, =rlm_spec_lang.pl:369-374=).  =evidence_policy/1= is a
requirement option, not a free-standing clause.  Mapping: goal ≈
=subject/1=; input ≈ subject/invariant data; require ≈ =require/2-3=;
constraint ≈ =invariant/1=; artifact ≈ =output_contract/1=; validate ≈
=assertion/2-3 + evidence_policy/1=; success ≈ =output_contract/1=.  Adding
a second, weaker SPEC vocabulary would violate the no-parallel-subsystem
rule; hardening =rlm_spec_lang= aliases is the coherent path if any alias is
wanted at all.

** F5: SPEC->PLAN binding exists; plans are fingerprint-bound.

=rlm_spec_workflow:spec_plan_bind/4= normalizes a plan through
=rlm_plan:plan_normalize= and attaches =spec_ref= (frozen fingerprint);
=spec_plan_execute/5= runs it through =rlm_outcome:plan_outcome/5=.  A
validate-style plan step can therefore be anchored to a frozen Spec without a
new verification stack.

** F6: rlm_graph is a state machine over node closures, not a plan-op DAG.

=rlm_graph= nodes resolve to trusted closures via a registry
(=normalize_registry_entry= requires callable, =prolog/rlm_graph.pl:243-265=;
fail-closed =validate_node_registry= 284-292); the module doc is lines 17-32
and spec/node/edge normalization is 86-237.  Edges are fixed/routed
transitions with visit limits, durable checkpoints and resume.  It is the
right *durability substrate* but compiling =step/depends_on= scheduling
directly onto it would either misuse node semantics or require a graph-per-step
encoding; conversely using it as the model-facing plan language contradicts
F1.

** F7: Plans are strictly sequential today; no sibling-dependency DAG.

=execute_steps/5= runs the step list left to right; =parallel/2= branches
execute *sequentially* (=execute_branches/8=, =rlm_plan.pl:1150-1182=;
=max_parallel= caps only the static estimate); =retry/3= multiplies
estimates.  Nothing expresses "s4 depends on s1..s3, s5 depends on s2" inside
one plan, and =ready_step/1=, =depends_on/2=, =step/2= are defined in no
loaded module (verified by =predicate_property= scans).

** F8: No project-op vocabulary and no symbol/span contract.

The only executable op reaching non-context work is generic =tool/3=.  There
are no typed =sync_remote/index/locate/diff/edit/...= constructors, no
=symbol_ref= / =source_span= data contract, and no bounded resolver.
=rlm_project_source= owns file/language/grammar *identity* (#95) but "does
not traverse syntax trees, run Tree-sitter queries, normalize symbols"
(=docs/project-source-registry.md=); semantic extraction is #96-#99, still
open.

** F9: Delegation with capability narrowing exists.

=spawn_agent(Spec, Capabilities, Bind)= desugars to =tool(spawn_agent, ...)=
(=rlm_plan.pl= lines 120-124, 168-177); narrowing itself is
=rlm_tool:capabilities_narrow/3= (=rlm_tool.pl:84-111=, =widening_denied=
on any non-subset) wired into spawn at =rlm_agent.pl:226-243=.  The handler
is host-supplied in the tools registry.  A =delegate/2= project op must
narrow through this path, not widen it.

** F10 (adversarial-review evidence, Q5/Q9): composition traps in the
planned composition path.

- =rlm_outcome:plan_outcome/5= folds ALL exceptions — including
  =rlm_cancelled= — into =execution_outcome{status:exception}=
  (=rlm_outcome.pl:877-885=) while =rlm_plan:plan_execute= rethrows
  cancellation (=rlm_plan.pl:1479-1481=).  A scheduler consuming
  =plan_outcome= outcomes must special-case cancellation or it will keep
  scheduling after cancellation.
- Each top-level =plan_run= starts a fresh =runtime_budget=
  (=rlm_plan.pl:820-837=); per-class budgets do NOT aggregate across
  separate executions, so a graph layer must thread an aggregate budget
  across steps.
- Capability terms form a closed grammar =capability_shape/1=
  (=rlm_tool.pl:127-140=) admitting =tool(Name)= but not =plan_op(Name)=;
  the per-op capability term for a desugared op must be =tool(Op)=.

* Inference (revised after adversarial review; design record finalizes)

- I1: A new sibling module =rlm_plan_graph= (like =rlm_spec_workflow= composes
  =rlm_plan=) is the coherent shape: it owns *plan-graph data* (parse,
  normalize, validate, ready-step scheduling, blocked propagation) and is a
  new closed front-end; =rlm_plan= remains the ONLY step executor (budgets,
  capability checks, tool dispatch, tracing).  Scheduling recipe pinned by
  review: =plan_graph_run_async/4= submits ONE execute predicate to
  =rlm_async=; the ready-step loop runs inside that single worker; each
  ready step's desugared plan calls =rlm_plan='s execute ABI directly (no
  nested Future waits); the synchronous facade awaits the same Future
  (AGENTS.md canonical direction; precedent =rlm_spec_workflow.pl:240-244=).
- I1a (review D4): the desugared artifact per step is minimally
  =[tool(Op, literal(StepArgs), StepBind), final(var(StepBind))]= —
  =rlm_plan= requires exactly one trailing =final/1=; step results route
  through the plan binding and are charged against the step's output-byte
  allowance.
- I2: The closed op vocabulary is data: =plan_graph_op(Name/Arity)= style
  declarations plus per-op argument shape validation; the required capability
  term for op =Op= is exactly =tool(Op)= (review D3: =plan_op(...)= is
  outside the closed =capability_shape/1= grammar; =tool(spawn_agent)= is
  the precedent).  The graph layer must validate the op name against the
  closed vocabulary BEFORE desugaring, so a model can never name a
  host-registered tool outside the 12-op vocabulary.  Desugared plan and
  inner capability term derive mechanically from the single
  =plan_graph_op/2= declaration, with a pairing test per op (review D7).
- I3: =validate/1= steps reference a frozen Spec ref; execution routes
  through the host verifier path — inside the async worker,
  =rlm_verify='s direct execute ABI (=spec_observe_execute/5=; guarded entry
  =spec_observe/5=) — never model self-report.
- I4: =symbol_ref= / =source_span= are closed ground data with structural
  validation; a bounded resolver over *host-supplied index facts*
  (=symbol_definition(SymbolRef, SourceSpan, Provenance)=) yields
  =ok(Span) / error(unresolved|ambiguous|unsupported)=.  Extraction remains
  #96-#99; plans speak =symbol(foo)=, adapters resolve spans (language
  independence).
- I5: Model-facing JSON shape (parity with =docs/typed-plans.md=):
  ={"steps":[{"id":"s1","op":"index","args":{...}}],
  "depends_on":[{"step":"s2","requires":["s1"]}]}=.  Snake_case op names match
  repository convention; the request's camelCase spellings are aliases at
  most.
- I6: Failure semantics: a failed step marks dependents =blocked=
  (structured, inspectable); =ready_step= only admits steps whose
  dependencies are =completed=.  Cancellation is NOT ordinary failure: a
  step outcome carrying =error(rlm_cancelled(Token), _)= aborts the whole
  graph and rethrows the token — no further step executes, no re-submission
  (review D1).  =abandoned= is terminal state, never retry authorization
  (AGENTS.md external-effect invariant).
- I6a (review D2): an aggregate graph budget bounds totals across step
  executions (steps, tool calls, model calls, context ops, output bytes);
  per-step plan budgets are derived from the remaining aggregate
  (=plan_result.budget_remaining= feed-forward) so N steps can never exceed
  the graph allowance.
- I7: Contract-presence gate: =scripts/plan_graph_contract_check.pl= holds one
  Prolog fact per required public surface (module exports incl. the
  async-first entry =plan_graph_run_async/4= and cancellation token
  =plan_graph_cancel/1=, closed vocabulary, validator rejections, scheduling
  semantics, resolver states, docs links); a bash wrapper loops over the
  facts until all are defined.  Presence gate only — never cited as
  behavioral evidence.
- I8 (review D6): op effect classification is explicit.  =sync_remote/1=,
  =edit/2=, =create/2=, =delete/1=, =run/1= are externally effectful in real
  use; their expert handlers must admit/dispatch/observe through the durable
  =rlm_effect= boundary (normalize -> schema/capability -> authority ->
  durable admission -> dispatch -> observe-or-indeterminate) with adapter
  identity/attempt lineage as trusted runtime data.  THIS SLICE adds no new
  external-effect path: shipped expert handlers in tests are pure
  host-supplied closures; docs state the requirement for real expert packs.
- I9 (review D8): =delegate/2= desugars through the existing
  =tool(spawn_agent, ...)= path with child capabilities validated as a
  narrowing subset by the graph validator (narrowing-by-default exercised in
  this slice, reusing =rlm_tool:capabilities_narrow/3= semantics).

* Rejected / avoided alternatives

- R1: Extending =rlm_plan.pl= in place with a project-op family and DAG
  scheduler — inflates a stable 1632-line core, mixes graph scheduling with
  sequential execution, larger regression blast radius.  Issue #288 goal-1
  wording ("data constructors in the existing =rlm_plan= closed-AST world")
  is read as: ops land as validated =tool(Op)= closed-AST steps executed by
  =rlm_plan= — the closed-AST *world*, not the file; issue text reconciled in
  the same slice.
- R2: Compiling step/depends_on onto =rlm_graph= nodes directly — conflates
  trusted node closures with plan-op data; edges/routes/checkpoint semantics
  are not dependency semantics; would need graph-per-step encodings.
- R3: A second SPEC vocabulary =spec(SpecId,[goal(...), ...])= — F4 shows the
  existing closed SPEC language already covers the semantics; a parallel
  vocabulary would fragment validation/freezing/fingerprinting.
- R4: Executing ops directly in Prolog (e.g. =call(sync_remote(Origin))=) —
  violates the core authority invariant; model data must never become a goal.
- R5: Tree-sitter-based semantic extraction inside this slice — owned by
  #96-#98; this slice only defines the consumption contract (YAGNI).

* Acceptance experiments / tests (planned)

- Parse: JSON and term forms -> closed graph AST; unknown op / unknown
  dependency / duplicate id / cycle rejected before execution.
- Scheduling: =ready_step= admits only dependency-complete steps; topological
  order exercised via host-recorded expert call order; failure blocks
  dependents with structured =blocked= outcomes.
- Authority: capability denial per op (=tool(Op)= terms); expert closure
  resolution fails closed when registry missing the op; no =call/1= on model
  data anywhere; vocabulary validated before desugaring.
- Cancellation: cancel mid-step aborts the graph, rethrows the token, and no
  further ready step executes (review D1 regression test).
- Budget: step count bound AND aggregate per-class bounds across steps
  (N steps cannot exceed aggregate tool/model/context/output allowances,
  review D2 regression test); cancellation yields structured partial state.
- Delegate: child capabilities validated as narrowing subset (review D8/I9).
- Symbols: =symbol_ref= structural validation; resolver
  =ok/unresolved/ambiguous/unsupported= over host index facts; spans validated
  (bytes ordered); no filesystem or parser access in this layer.
- Async/sync parity: =plan_graph_run= awaits the same Future as
  =plan_graph_run_async=; one =rlm_async= submission total.
- Contract gate: =scripts/plan_graph_contract_check.sh= loops to green.
