** Design
- Ownership :: The spawned child identity owns the effective completion capability ceiling and authority context. Registration options remain host configuration but cannot override those two possession boundaries after spawn.
- Canonical path :: =spawn child -> normalize requested child capabilities -> replace completion capabilities -> replace authority_context with agent(RuntimeId, ChildId) -> child-owned completion execute=.
- Tool adapter :: Add =tool_registry_runtime_tools/4= to carry trusted invocation options into existing registry plan handlers; keep =/3= as the empty-options compatibility facade.
- Completion integration :: Extract only trusted tool invocation metadata from completion options and pass it through =tool_registry_runtime_tools/4=. Do not pass planner/model/callable configuration as tool metadata.
- Failure contract :: A planner-selected tool outside the spawned child ceiling fails through the existing capability boundary. Tool authority resolves against the child context and retains the existing approve/deny/pending semantics.
- Compatibility :: Direct completion callers and =tool_registry_runtime_tools/3= retain current behavior when no authority metadata is supplied.
- Verification :: Preserve the two red regressions, then cover agent-count, recursive-depth, parallel-width, token/time, unavailable, denied, cancelled, and failed subagent outcomes using deterministic existing boundaries.

** Adversarial review
- Duplicate =capabilities(...)= or =authority_context(...)= entries could make first-option semantics order-dependent; remove every existing instance before prepending the child-owned value.
- Trusting the raw requested capability list could retain duplicates or malformed values; normalize it through the canonical capability normalizer after successful spawn.
- Overriding =child_capabilities(...)= would silently widen recursive descendants; leave it intact so =rlm_completion= narrows it against the injected child ceiling and rejects widening.
- Passing all completion options into tool invocation could leak callables or unrelated policy; project only authority/correlation metadata.
- Replacing the registry's stored authority would couple concurrent children; pass an invocation-local child context instead.
- Calling the public async status facade from the bounded worker would nest Future waits; derive the opaque child context directly from trusted runtime/child identities.
- The change does not make model or KB data executable and does not add a scheduler, authority system, effect path, or recursive delegation bypass.

** Decision
- Auto-RAGE decision :: Accept the design above for realization. It binds existing completion and tool boundaries to the already-created supervised child, preserves compatibility, and repairs both demonstrated possession escapes without introducing parallel infrastructure.
