## VERDICT

**sound-with-changes.**

The findings F1-F9 are substantively accurate against the base commit (with citation defects and one real overstatement detailed below), and the rejected alternatives R1-R5 are all defensible. The design direction I1-I7 is the right shape, but as written it contains one empirically-proven correctness trap (cancellation swallowed by `rlm_outcome` would let a ready-step loop keep scheduling after cancellation), one budget hole (fresh budget per desugared step execution), one vocabulary mismatch (`plan_op/1` capability terms are outside the closed capability grammar), and one omission (the durable effect boundary required by both AGENTS.md and issue #288). All are fixable in the design record before implementation; none invalidates the sibling-module direction.

## DESIGN RISKS (ranked)

**D1 (highest, empirically proven): cancellation is swallowed by the named composition path.**
I1 executes each ready step "through =rlm_plan=/=rlm_outcome=" — i.e. via `rlm_outcome:plan_outcome/5`. `rlm_plan:plan_execute` correctly *rethrows* cancellation (`execution_exception(error(rlm_cancelled(Token),_), ...)` rethrows, `rlm_plan.pl:1479-1481`; empirically Q9a: `plan_run` throws `error(rlm_cancelled(tok),ctx)`). But `plan_outcome/5` catches **all** exceptions and folds them into `execution_outcome{status:exception, error:diagnostic_error{kind:exception,...}}` (`rlm_outcome.pl:41-43` catch + `unexpected_outcome_exception` 877-885; empirically Q9b/Q9c: the rlm_cancelled throw comes back as `status:exception` with the cancellation buried at `error.exception`, `budget_remaining:unknown`, no transitions). Consequence: a ready-step scheduler that treats `status:exception` as ordinary step failure will mark dependents `blocked` and **continue scheduling independent steps after cancellation**, violating I6's own sentence ("Cancellation ... produce structured partial outcomes, never silent success") and AGENTS.md's "Preserve ... cancellation semantics across wrappers". The design record must make cancellation propagation a named requirement with a test (cancel mid-step ⇒ no further step executes, token rethrown).

**D2 (empirically proven): per-step budget reset fragments the budget.**
Each desugared plan executed via `plan_run`/`plan_execute` starts from `initial_execution_state` (`rlm_plan.pl:820-837`) — a fresh `runtime_budget`. The "counters are shared across recursion, retry, and parallel branches" property (`docs/typed-plans.md:163-164`) holds only *within one plan execution*. Empirically Q5: two tool steps in one plan with `max_tool_calls:1` are rejected at validate (`budget_exceeded, estimated:2`), but two separate `plan_run` executions each with `max_tool_calls:1` both succeed — 2 total tool invocations. A 64-step graph therefore admits up to 64× the default per-step model/tool/context/output allowances unless the graph module threads an aggregate budget. I6's "step count bound" does not cover this. `plan_result.budget_remaining` is exposed by `finalize_execution` (`rlm_plan.pl:1362-1380`), so feed-forward accounting is implementable — but it must be specified and tested, not assumed.

**D3 (empirically proven): I2's capability terms are outside the closed capability grammar.**
I2 proposes per-op capability terms "e.g. =plan_op(sync_remote)=, =validate_spec=". The agent-level capability system is a closed grammar: `capability_shape/1` at `rlm_tool.pl:127-140` admits only `rlm, parallel, retry, checkpoint, tool(Name), context(Name), model(Name), graph(Name), persistence(Name), network(Name), filesystem(Name), process(Name), mcp(Name)`. Empirically Q4a: `capabilities_narrow([tool(a)], [plan_op(sync_remote)], O)` → `error(capability_error{kind:invalid_capabilities, detail:invalid_capability(plan_op(sync_remote))})`. Options the design record must choose between: (a) use `tool(<op>)` as the per-op capability term — consistent with the desugaring and with existing precedent (`docs/agent-runtime.md:359` "the plan must possess `tool(spawn_agent)`"); or (b) extend `capability_shape/1` with a `plan_op/1` family — a deliberate grammar widening that must be called out, tested, and documented, not slipped in. (c) A third option — a private plan-graph capability namespace unrelated to the agent grammar — would create two capability vocabularies and should be rejected.

**D4: "single-step closed-AST plan" is impossible as stated.**
Every `rlm_plan` plan requires exactly one trailing `final/1` (`rlm_plan.pl:417-422`); empirically Q3b: validating `plan([tool(t, literal(a), b)])` yields `error(... final_must_be_unique_and_last ...)`. The desugared artifact is minimally **two** steps — `[tool(Op, literal(StepArgs), StepBind), final(var(StepBind))]` — with the step result routed through `bind_value`/`consume_output` (`rlm_plan.pl:1108-1135`), i.e. charged against the (fresh, see D2) per-execution output-byte budget. Cosmetic in I1, but the design record should pin the exact desugar shape, the result plumbing, and the per-step output-byte accounting.

**D5: no async surface in the pinned public contract.**
The committed gate pins only `plan_graph_run/5` (`scripts/plan_graph_contract_check.pl:109-110`). Every precedent module with latency-bearing work exposes an async-first entry (`rlm_graph:graph_run_async/4`, `rlm_spec_workflow:spec_workflow_run_async/3`) because AGENTS.md:43 fixes the canonical direction: "`*_execute -> Future -> synchronous facade awaits the same Future`. Code already running inside a bounded async worker calls the trusted execute ABI directly rather than nesting Future waits." Step plans can invoke model providers, so the surface needs `plan_graph_run_async/4`-style entry (one `rlm_async_submit`, ready-step loop inside that single worker calling `rlm_plan` execute ABIs directly, sync facade awaiting the same Future). The contract script must pin the async entry too.

**D6: the durable effect boundary is absent from the design direction.**
Issue #288 states: "External effects (if any expert performs them) remain behind the durable effect boundary; this slice adds no new external-effect path." AGENTS.md:50-58 fixes the required order (normalize → schema/capability/policy → authority → durable admission → dispatch → observe-or-indeterminate). The research record never mentions `rlm_effect` / `rlm_effect_authority` anywhere, even though four of the twelve ops (`sync_remote/1`, `edit/2`, `create/2`, `delete/1`, `run/1`) are externally effectful in any real use. The design record must add an inference: which ops are classified externally effectful; that their expert handlers admit/dispatch/observe through `rlm_effect`; and that expert closure identity is trusted runtime data, never caller/model metadata (AGENTS.md external-effect invariants). Without this, an expert handler that "just does the work" in plain Prolog is the default outcome.

**D7 (speculation, risk-management): dual-layer drift.**
By issue mandate the graph module *is* a second language front-end (its own parse/normalize/validate/schedule); the AGENTS.md invariant it must respect is not duplicating the *executor* or *scheduler*. The residual risk is drift between the graph layer's per-op argument validation/capability terms and `rlm_plan`'s re-validation of each desugared tool step (e.g. graph layer grants `plan_op(sync_remote)` while the inner plan requires `tool(sync_remote)`). Mitigation to prescribe: derive the desugared plan and its inner capability term mechanically from the single `plan_graph_op/2` declaration, and add a pairing test per op. Labeled speculation because it is a controllable risk, not a defect in the record.

**D8 (speculation): Q2's `error(unsupported)` option for `delegate/2` sits awkwardly with the committed contract and the issue invariant.**
The gate requires tests mentioning `delegate` (`scripts/plan_graph_contract_check.pl:144-145`) and the issue requires "Child/delegate capabilities narrow by default". If delegate ships vocabulary-only, the docs must state that narrowing is unexercised this slice and the contract fact should say so, or reviewers will read the test as evidence of narrowing behavior.

### On the "second plan interpreter / second scheduler" question (I1)

- **Second scheduler:** No violation in the shape proposed, provided the surface follows AGENTS.md:42-43. A ready-step loop is data-dependent ordering (same class as `execute_steps/5`), not a thread scheduler. Concretely safe recipe: `plan_graph_run_async` submits **one** execute predicate to `rlm_async`; the loop runs inside that worker; per-step work calls `rlm_plan`'s execute path directly (exactly what `rlm_spec_workflow` node handlers do with `spec_observe_execute` at `rlm_spec_workflow.pl:239-244`, and what `rlm_verify`'s doc mandates, `rlm_verify.pl:15-16`). What would violate: per-step Futures, a second worker pool, or calling `spec_observe_async` + `rlm_future_await` from inside a step. The record should state this recipe explicitly.
- **Second plan interpreter:** The ready-step loop + desugar is a new *front-end*, which issue #288 itself mandates; the invariant worth defending is that `rlm_plan` remains the **only** step executor (budgets, capability checks, tool dispatch, tracing). The desugar-through-`rlm_plan` construction preserves that, subject to D2/D3/D7. I1's comparison to `rlm_spec_workflow` is apt: that module's own doc says "It does not schedule work or interpret a new plan language" (`rlm_spec_workflow.pl:12-19`) — note the difference: `rlm_plan_graph` *will* interpret a new language, so the design record should not lean on the "deliberately thin" precedent too hard; the honest framing is "new closed vocabulary + scheduler, reused execution substrate".
- **Can model data reach `call/1`?** Not under the proposed shape, with one condition. The only `call` of model-influenced data is `call(Handler, Args, ToolResult)` (`rlm_plan.pl:945`), where `Handler` comes from the host registry by exact atom match (1358-1360) and registry entries are validated `callable` (780-787); model data is the *argument*, never the goal. The condition: the op name flowing from model JSON must be validated against the closed `plan_graph_op/1` vocabulary **before** desugaring to a tool step — otherwise a model could name any host-registered tool outside the 12-op vocabulary and reach tools it was never granted as plan ops (capability denial at `rlm_plan` would still require the matching `tool(<op>)` capability, but the graph layer must not widen the name space). The record's I2 already says this; the design record must make the ordering (validate-then-desugar) explicit and tested.

## REJECTED ALTERNATIVES

- **R1 (don't extend `rlm_plan.pl` in place): sound.** 1632 lines today (the record says "~1500" — trivial drift), stable public surface of six exports (Q1), and mixing a dependency scheduler into `execute_steps/5` would entangle two execution models. Caveat: issue #288 goal 1 says ops are "data constructors in the existing `rlm_plan` closed-AST world" — defensible as "the rlm_plan closed-AST *world*" (ops land as validated `tool/3` steps), but the wording points the other way and must be reconciled in the issue text (see REQUIRED CHANGES).
- **R2 (don't compile onto `rlm_graph` nodes): sound, with one nuance.** A *pure linear chain* is expressible today (fixed edges, one start edge — `rlm_graph.pl:294-300`), so the rejection is decisive for general DAGs/diamonds, not for chains: edges are static, routers route on state not dependencies, and `max_visits_per_node`/checkpoint semantics are not dependency semantics. The coherent split the record hints at in Q3 — reuse `rlm_graph_persist` as a durability substrate while keeping node semantics out — is coherent and should be named.
- **R3 (no second SPEC vocabulary): sound** despite F4's overstatement; the existing catalog strictly covers the requested clause set.
- **R4 (no `call(sync_remote(...))`): sound**, matches the core authority invariant; empirically the runtime already rejects such output (Q3a/Q8) and nothing in the design re-introduces it.
- **R5 (no tree-sitter extraction in slice): sound**, verbatim ownership statement in `docs/project-source-registry.md:24`.

## REQUIRED CHANGES (must-fix before implementation)

1. **Cancellation propagation requirement (D1).** The design record must specify: a step outcome whose `error.exception` is `error(rlm_cancelled(Token), _)` aborts the whole graph (rethrow, terminal), is never treated as ordinary step failure, and never authorizes re-submission. Add a PlUnit test: cancellation mid-step ⇒ no further ready step executes and the token propagates. (Evidence: Q9a/Q9b, `rlm_outcome.pl:877-885`, `rlm_plan.pl:1479-1481`.)
2. **Aggregate graph budget (D2).** Define graph-level bounds on total model/tool/context ops and output bytes across step executions, not just step count; specify the feed-forward mechanism (`plan_result.budget_remaining`) and a test proving N steps cannot exceed the aggregate. (Evidence: Q5a/Q5b, `rlm_plan.pl:820-837`, `docs/typed-plans.md:163-164`.)
3. **Capability-term reconciliation (D3).** Choose `tool(<op>)` terms or explicitly widen `capability_shape/1` (`rlm_tool.pl:127-140`); either way document the graph-layer ↔ plan-layer capability mapping and test denial per op. Do not leave `plan_op(sync_remote)`/`validate_spec` in the record as-is (Q4a proves they are invalid today).
4. **Fix the desugar shape (D4).** Replace "single-step closed-AST plan" with the actual minimal form `[tool(Op, literal(Args), Bind), final(var(Bind))]` and specify result plumbing + per-step output-byte accounting.
5. **Add the durable-effect-boundary direction (D6).** New inference item: classify which ops are externally effectful; require their experts to go through `rlm_effect` (normalize → admit → dispatch → observe/indeterminate); state that this slice adds no new external-effect path (issue #288 invariant; AGENTS.md:50-58).
6. **Async surface in the pinned contract (D5).** Add `plan_graph_run_async` (+ cancellation token) to `scripts/plan_graph_contract_check.pl:99-118` and specify the canonical direction: one `rlm_async_submit`, ready-step loop inside the worker, synchronous facade awaits the same Future (AGENTS.md:42-43; precedent `rlm_spec_workflow.pl:94-100`).
7. **Reconcile issue text (process).** Issue #288 goal 1 ("data constructors in the existing `rlm_plan` closed-AST world") vs the sibling-module direction must be reconciled in the same slice per AGENTS.md GitHub-state discipline (either reword the issue or add an explicit reading note in the design record). Also state I6's `abandoned`-is-terminal rule explicitly (issue invariant: "`abandoned` semantics stay terminal") — I6 currently covers `blocked` and cancellation but not `abandoned`.
